# AGENTS.md

Guidance for agentic/AI-assisted work on this repo. `thunderstorm` is a small ActiveRecord/ActiveModel-style ORM for TypeScript, built on [Knex](https://knexjs.org). Read [README.md](README.md) first for the feature-by-feature reference with runnable snippets — this file is about _how the codebase is put together_ and _what not to accidentally undo_.

## Layout

```
src/
  AttributeModel.ts — attributes/casting/virtual/defaults, validations, dirty tracking, serialization — no DB
  Model.ts           — extends AttributeModel: persistence, querying, associations, callbacks, QueryChain, connect()/transaction()
  decorators.ts      — @Column, @Validates, callback decorators, @Delegate, @Enum, Timestamped/Lockable/SecurePassword/SecureToken mixins
  attachments.ts     — @HasOneAttached/@HasManyAttached, BlobStorage, attachmentColumns()/createAttachmentTable() migration helpers
  dependent.ts       — @Dependent(associationMethod, action) — cascades destroy/delete/update/restrict to related records
  counterCache.ts    — @CounterCache(associationMethod, column) — auto-maintained count column on a belongsTo/hasOne's parent
  encryption.ts      — encryptedCaster() (AES-256-GCM column encryption) — a Caster, not a decorator
  casters.ts         — built-in attribute casters (string/number/boolean/date/json)
  security.ts        — password hashing (scrypt) and token generation primitives, used by the SecurePassword/SecureToken mixins
  errors.ts          — Errors, RecordInvalid, RecordNotSaved, StaleObjectError
  index.ts           — public API surface (the only file consumers should import from)
  example/demo.ts    — exercises every feature end-to-end against a real in-memory DB
  *.test.ts          — one file per feature area (see README's Testing section)
migrations/          — schema source of truth, run via the Knex CLI (knexfile.ts)
```

## Before making changes

Run the full check before and after any nontrivial change — this is exactly what CI (`.github/workflows/ci.yml`) runs:

```bash
npx tsc --noEmit && npm run lint && npm run format:check && npm test
```

`npm run demo` is also worth running for anything touching `Model.ts` or `decorators.ts` — it's the closest thing to an integration smoke test and has caught real bugs (see below) that the unit tests alone hadn't.

## Load-bearing design decisions — don't undo these by accident

- **No `[key: string]: any` on `AttributeModel`/`Model`.** It was removed deliberately so typos on undeclared properties are compile errors. Internal code that needs to read/write a column by a runtime string key uses the `getAttr`/`setAttr` helpers exported from `AttributeModel.ts` (imported into `Model.ts` too), not direct index access. If you add a new method that needs dynamic attribute access, use those helpers rather than re-adding a blanket index signature.
- **Metadata maps (`COLUMNS`/`VALIDATIONS`/`CALLBACKS`) must deep-clone on inherit.** `ownMetadataMap` in `decorators.ts` seeds a subclass's own map with cloned copies of whatever its ancestor already registered, rather than starting empty. This was a real bug: `Timestamped(Model)` registers `createdAt`/`updatedAt` + callbacks on an intermediate class, and a further subclass adding its own `@Column()` used to silently lose them. If you add a new metadata symbol following this pattern, route it through `ownMetadataMap` too — don't hand-roll the `hasOwnProperty` check again without the clone step.
- **Decorators are TC39 Stage 3, not legacy `experimentalDecorators`.** Metadata lives on each class's `[Symbol.metadata]` object (which the engine automatically parents to the superclass's, giving the deep-clone-on-inherit behavior above almost for free via `ownMetadataMap` operating on that object instead of the constructor directly) rather than directly on the constructor via a bespoke symbol key. Two consequences worth knowing if you touch `decorators.ts`:
  - `Symbol.metadata` isn't natively supported by Node yet, and TypeScript's decorator helpers silently no-op `context.metadata` without it — hence the one-line polyfill at the top of `decorators.ts` (`(Symbol as any).metadata ??= Symbol.for('Symbol.metadata')`), which must keep running before any decorated class loads.
  - Any class with at least one decorated field gets standards-compliant "always define" field semantics for **every** field it declares, even undecorated ones with no initializer — this isn't a `useDefineForClassFields` toggle, it's inherent to how TC39 decorators are specified, and both esbuild (Vitest) and `tsc`/ts-node apply it. `@Column()`/`@PrimaryKey()`/`@Validates()` compensate for their own fields via `preserveFieldValue` (an initializer that re-affirms whatever `Object.assign`/the default-application loop already put on `this`, both of which run before any subclass field initializer does). An _undecorated_ bare field sharing a class with a decorated one — the "custom accessor" backing-field pattern in README — has no decorator to do that for it, so it must be declared with `declare` (`declare private _code: string;`), not a real field, or it'll silently reset to `undefined` after `super()`. Mixins (`Timestamped`/`SecurePassword`/`SecureToken`) inject metadata without going through an actual decorator application, so they synthesize their own `[Symbol.metadata]` object via `ownClassMetadata` — route any new mixin the same way rather than assigning `ctor[SYMBOL]` directly.
- **`assignRow` only assigns declared `@Column()` fields**, not every key in a raw DB row. It used to blindly assign everything `SELECT *` returned, which crashed a custom setter when an undeclared column came back as `null`. Keep it that way — declared columns are the contract, not the table's actual shape.
- **Relations (`hasMany`/`hasOne`/`belongsTo`, `hasManyThrough`/`hasAndBelongsToMany`, and `belongsToPolymorphic`/`hasManyPolymorphic`/`hasOnePolymorphic`) are all plain instance methods, not decorators.** They take the related class directly (no thunk) because the reference is only resolved when the method _runs_, well after both modules have finished loading — safe even across circular imports between two model files. A decorator-based approach would evaluate the class reference too early and break on circular imports.
- **`hasManyThrough`/`hasAndBelongsToMany` stay lazy by building one query with a `whereIn(pk, subquery)`, not two sequential round-trips.** `through.query()`/`getKnex()(joinTable)` becomes a Knex subquery passed straight to `.whereIn()` rather than being awaited separately — this is what lets the result stay a chainable `QueryChain` exactly like `hasMany`, instead of an eagerly-resolved array. `preloadHasManyThrough`/`preloadHasAndBelongsToMany` can't use that trick (they need the join rows in JS to group them per-record), so they're genuinely two awaited queries — still O(1) regardless of record count, just not O(1) queries in the literal sense the single-record path is. Both preload variants share their grouping logic via the module-level `groupAndAttachThrough` helper — the only difference between them is how `joinRows` get fetched, so don't duplicate that logic if you add a third many-to-many flavor.
- **There's no join-row uniqueness enforcement in `associate()`.** Same reasoning as `@Validates({ uniqueness })` elsewhere: pair it with a real unique index/constraint on `(sourceKey, targetKey)` in the migration for actual correctness under concurrency, not just app-level discipline.
- **Polymorphic type strings are an explicit map (`{ post: Post, photo: Photo }`) the caller provides, never inferred from `ctor.name`.** This was a deliberate choice, not an oversight — Rails defaults to the class name as the type discriminator, which silently orphans every existing row referencing a class that later gets renamed unless a data migration also runs. Every other place a model needs to be identified in this library (`tableName`, `foreignKey`) is already explicit, never derived from the class — polymorphic types follow the same rule. Don't add an implicit-class-name fallback without discussing the breaking change first.
- **`preloadBelongsToPolymorphic` can't be a single query the way `preloadBelongsTo` is**, since different records may reference different target tables. It groups `records` by their type-field value first, then runs one batched query per distinct type actually present — bounded by the number of distinct types, not the record count, but genuinely `types.size` queries in the worst case, not `1`. Keep that distinction in mind if you touch its query-count assumptions elsewhere (e.g. in a test).
- **`@Delegate`/`@Enum` stay class decorators; `Timestamped` is a mixin, not a decorator.** The difference is deliberate: `Timestamped`'s added properties (`createdAt`/`updatedAt`) are fixed names, so a mixin gives them real static types for free. `@Delegate`/`@Enum` generate member _names_ from runtime string values, which a decorator can't feed back into the type system — consumers type those via companion `interface` declarations (see README's "TypeScript typing notes"). If you add a similar macro, prefer a mixin whenever the generated member names are fixed at the call site; only reach for a decorator + documented interface-merging when they're genuinely dynamic.
- **`beforeValidation`/`afterValidation` are intentionally not implemented.** Wiring them up would force `isValid()` to become async, breaking its current synchronous contract and a large chunk of the validation test suite. Don't add them without discussing the breaking change first.
- **`transaction()` has no savepoint/nested-transaction support by design** — a nested call just reuses the outer transaction via `AsyncLocalStorage`. Don't add real savepoints without also handling partial rollback semantics carefully.
- **`AttributeModel`/`Model` split follows Rails' ActiveModel/ActiveRecord line exactly.** `AttributeModel` (attributes, casting/virtual/defaults, validations, dirty tracking, serialization) has zero knowledge of persistence — no `tableName`, no `getKnex()`, no DB connection required even to import it. `Model extends AttributeModel` adds everything table-shaped: `query`/`find`/`all`/`where`, associations, `save`/`destroy`/`reload`/`dup`, and lifecycle callbacks. When adding a new feature, decide which layer it belongs on _before_ implementing: if it needs a table or a query, it's `Model`-only; if it's purely about an attribute's value (a new caster, a new validation rule, a new serialization option), it belongs on `AttributeModel` so `AttributeModel`-only subclasses get it too. Fields/methods that `Model` needs from `AttributeModel` but shouldn't be public (`snapshotAttributes`, the previous-changes setter) are `protected`, not `private` — `private` on `AttributeModel` is invisible to `Model`'s own methods, unlike within the old fused class.
- **`@Validates({ uniqueness })` is a `Model`-only rule despite living in the shared `ValidationRule` type.** `AttributeModel.applyRule()` silently ignores the `uniqueness` key (it has no table to check); `Model.save()` runs a separate `checkUniqueness()` after `isValid()` passes. Don't try to make `isValid()` async to unify these — that's the same tradeoff already made for `beforeValidation`/`afterValidation` above, and it's deliberate.
- **`@Column({ guarded: true })` affects two unrelated code paths on purpose: `permit()` (incoming) and `serializableHash()`/`toJSON()` (outgoing).** This was originally two separate ideas (mass-assignment protection, then password-digest leaking into JSON) that turned out to be the same underlying signal — "this must never cross an untrusted boundary in either direction." If you touch one of those code paths, check whether the change should apply to the other too.
- **`SecurePassword`'s password-hashing callback checks `isAttributeChanged('password')`, not `password === undefined`.** `password` is virtual, so it never auto-clears after being set — without checking dirty tracking, every subsequent `save()` of the same in-memory instance would re-hash the same unchanged password with a fresh salt (caught by a real test failure, not a review comment — see `security.test.ts`). This is a concrete example of `AttributeModel`'s dirty tracking being useful outside of `changes`/`isChanged` themselves.
- **`@HasOneAttached`/`@HasManyAttached` (`attachments.ts`) deliberately don't own storage, only orchestrate it.** `BlobStorage` is a two-method interface (`put`/`delete`) the caller provides — no `get`/`url`/variants, since serving a file back out is a deployment-specific, controller-shaped concern outside an ORM's job. `storage` is a **required** constructor argument on both decorators on purpose: a model can't be decorated without a way to clean up after itself, which is what makes destroy-time auto-purge a guarantee rather than something callers have to remember to opt into. Both decorators register their own `afterDestroy` callback via the now-exported `ownColumns`/`ownCallbackList` from `decorators.ts` (the same internal metadata plumbing `@Column()`/mixins use) — if you add a third attachment-like macro, route it through those too rather than reinventing metadata storage. Destroy-time cleanup is synchronous and best-effort, not transactional (no job queue backs it) — a `storage.delete` failure during `destroy()` makes the call reject even though the DB row is already gone; don't paper over that by swallowing the error, it's the honest signal that cleanup needs a retry. `attach*` calls `storage.put` before persisting metadata — if the following DB write fails, it best-effort deletes the now-orphaned blob but re-throws the original error rather than the cleanup error, so a narrow leak window under simultaneous storage-and-DB flakiness is a known, accepted gap, not a bug to silently fix by masking errors.
- **`encryptedCaster()` (`encryption.ts`) is a `Caster`, not a decorator.** `ColumnOptions.type` already accepts an arbitrary `Caster` object, and encryption is exactly a load/save transform like any other caster — no new decorator, no new metadata mechanism, nothing added to `decorators.ts`. Deterministic mode derives its IV via `HMAC-SHA256(key, plaintext)` rather than reusing a fixed IV — this is what makes identical plaintexts produce identical ciphertext (queryable) while still giving different plaintexts distinct IVs (avoiding AES-GCM's catastrophic same-IV-different-plaintext failure mode). Key rotation (`keys: [current, ...old]`, tried in order on decrypt) only covers _reads_ of existing rows — it is **not** automatic re-encryption. Re-saving the same JS-level value doesn't rewrite the column, because dirty tracking only sends columns whose value actually changed; migrating rows off an old key needs a script that forces the write.
- **`Model.where()`/`QueryChain.where()` cast condition values via the shared `castConditions()` helper, same as `save()`/`checkUniqueness()` already did.** Before this, condition values passed straight to Knex uncast — silently broken for any caster whose DB representation differs from the JS value (a `json` column, `encryptedCaster`), though it went unnoticed for booleans/dates since the driver layer coerces those independently. `castForWrite` is a `static` method (not per-instance) specifically so both the static `Model.where()` and `QueryChain.where()` (which only holds `modelClass`, not an instance) can reach it — don't move it back to instance-only without re-solving that.
- **`QueryChain.deleteAll()`/`destroyAll()` mirror Rails' `delete_all`/`destroy_all` split on purpose — don't collapse them into one method.** `deleteAll()` is a single bulk `DELETE`, no callbacks, O(1) queries; `destroyAll()` loads every matching row and calls `destroy()` on each, so `beforeDestroy`/`afterDestroy` (and anything they do — `@HasManyAttached`'s auto-purge, a `destroy()` override like preventing an image's blob from leaking) run exactly as if called individually, at the cost of one query per record. Picking the wrong one silently either skips cleanup that was relied on (`deleteAll()`) or turns a bulk operation into N+1 queries for no reason (`destroyAll()` where nothing actually needed the callbacks) — the choice belongs to the caller, who knows whether the target model has destroy-time side effects worth preserving, not to the library. Both return the count affected, not the record count matched — for `destroyAll()` those can differ if a `beforeDestroy` callback blocks some of them.
- **`Model.insertAll(rows)` is the create-side counterpart to `deleteAll()`, not to `destroyAll()` — there's no "loop and `create()` each row" bulk-insert variant.** `create()`'s per-record machinery (defaults, validations, `beforeSave`/`beforeCreate`/`afterCreate` callbacks) is exactly what makes many models function correctly — `Timestamped` stamps `createdAt`/`updatedAt`, `SecureToken` generates its token, `SecurePassword` hashes the password — all via callbacks, not defaults, so there's no cheap way to keep those working while still doing one bulk `INSERT`. `insertAll()` is honest about this instead of pretending otherwise: it skips all of it, the same trade `deleteAll()` already makes, and each row must supply every column the caller needs populated. It reuses the same `castConditions()` helper `where()`/`updateAll()` already use, so caster-backed columns (`json`, `encryptedCaster`) are still written correctly — casting isn't part of the AR-machinery it's skipping. Returns `rows.length`, not a driver-reported count, since Knex's multi-row `insert()` return shape isn't consistent across drivers (SQLite hands back only the last inserted id) and a bulk insert either fully succeeds or throws — there's no partial-success count to report the way `update`/`delete` have.
- **`@Dependent(associationMethod, action)` (`dependent.ts`) is a class decorator naming an already-defined association _method_ by string, not a parameter on `hasMany`/`hasOne`.** Those two only exist as plain per-call instance methods, not a persistent association registry (see the `hasMany`/`hasOne`/`belongsTo` bullet above) — there's no object a `dependent:` option could attach to at declaration time the way Rails' `has_many ... dependent: :destroy` does. `@Dependent` instead wires cleanup onto `beforeDestroy`/`afterDestroy` via the same `ownCallbackList` metadata plumbing `attachments.ts` already established, and at runtime calls the named method and duck-types the result via `.destroyAll` to decide whether it's chain-shaped (`hasMany`/`hasManyThrough`/`hasAndBelongsToMany`) or a single record (`hasOne`/`belongsTo`) — so the same decorator works for both without the caller specifying which. `'restrict'` is the one action that runs as `beforeDestroy` instead of `afterDestroy` (it has to block the destroy, not clean up after it) and is checked via `.exists()`/truthiness rather than loading records. `{ update: {...} }` on a single-record association deliberately calls `.update()` on that record (not a scoped `deleteAll`-style bulk statement) since there's only ever one row and `update()` already runs the right callbacks for it.
- **`Lockable` (optimistic locking) is enabled by a hardcoded `lockVersion` column name, checked directly in `Model.save()`/`destroy()` — not a callback, and not a generic "any column can be the lock column" option.** This mirrors Rails' own `lock_version` convention rather than inventing configurability nothing asked for. It has to live in `save()`/`destroy()` themselves (guarded by `ctor.columns.has(LOCK_COLUMN)`) rather than in the `Lockable` mixin as a `beforeUpdate`/`beforeDestroy` callback, because a callback can only bump the in-memory value — detecting a lost race requires the UPDATE/DELETE's own `WHERE lockVersion = <the version this instance was loaded with>` clause and checking the affected-row count, which only the query-issuing code itself can do. `StaleObjectError` is thrown, not returned as `false`/reported via `errors` — unlike a normal validation failure, a lost race isn't safe to silently swallow, so `save()`/`update()`/`destroy()` all raise it even in their non-`OrFail` form (the one place a non-`OrFail` method throws). `insertAll()`/`updateAll()`/`deleteAll()`/`destroyAll()` don't go through `save()`/`destroy()` at all, so they silently bypass the lock check — same trade-off those already make by skipping callbacks/validations, documented rather than special-cased away.
- **`@CounterCache(associationMethod, column)` (`counterCache.ts`) uses `.increment()`/`.decrement()` — a single atomic `UPDATE ... SET column = column + 1` — never load-then-save.** A load-then-save (`parent.commentsCount++; await parent.save()`) would race under concurrent creates/destroys: two children created at nearly the same moment could both read the same starting count and both write the same incremented value, silently losing an increment. `.increment()`/`.decrement()` push the arithmetic into the SQL itself, so it's correct under concurrency without needing a transaction. Deliberately does **not** handle foreign-key reassignment (moving a child to a different parent) — doing that correctly needs the foreign key column name threaded through explicitly to diff the old and new parent, which the decorator only knows as "whatever association method resolves it," not a column name. Same shape as `@Dependent`: names an existing association method rather than adding a param to `hasMany`/`belongsTo`.
- **`QueryChain.lock()` (pessimistic locking) is a thin wrapper over Knex's `.forUpdate()`/`.forShare()` — no new abstraction, no attempt to enforce it's called inside `transaction()`.** A `SELECT ... FOR UPDATE` outside a transaction "works" (doesn't error) but is pointless — Postgres/MySQL release the lock the instant the statement completes since there's no surrounding transaction to hold it across — but the library doesn't hard-block this, matching its general non-paternalistic style elsewhere (e.g. `insertAll()`/`deleteAll()` don't stop you from using them somewhere their trade-offs don't fit either). SQLite has no row-level locking at all and silently no-ops `.forUpdate()`/`.forShare()` rather than erroring, so the sqlite-backed test suite can only verify the method is chainable and doesn't corrupt the query — not that it actually blocks a concurrent transaction, which would need a real Postgres/MySQL instance to test.

## Testing conventions

- Vitest, and tests run against **real `sqlite3 :memory:` connections** — no mocking of Knex or the DB layer. Each test file creates its own tables in `beforeEach`.
- One file per feature area (`validations.test.ts`, `callbacks.test.ts`, `associations.test.ts`, `dirty.test.ts`, `casting.test.ts`, `macros.test.ts`, `scopes.test.ts`, `transactions.test.ts`, `convenience.test.ts`, `queries.test.ts`, `attributes.test.ts`, `attributeModel.test.ts`, `permit.test.ts`, `uniqueness.test.ts`, `security.test.ts`, `attachments.test.ts`, `encryption.test.ts`, `dependent.test.ts`, `locking.test.ts`, `counterCache.test.ts`, plus `decorators.test.ts`/`errors.test.ts` for pure-metadata/unit-level checks). Add new tests to the matching file rather than creating a new one per test case.
- `attachments.test.ts` injects an in-memory `FakeStorage` test double (a `BlobStorage` implementation backed by a `Map`) rather than mocking Knex — this isn't the "no mocking" rule being broken, `BlobStorage` is an explicitly caller-provided boundary (like bringing your own Knex driver), so faking it is the correct thing to inject, unlike faking the DB layer itself.
- When testing N+1-avoidance or query counts, assert the actual count via `knex.on('query', () => queryCount++)` — don't just assert on the resulting data, which wouldn't catch a regression back to one-query-per-record.
- `tsconfig.json` excludes `*.test.ts` from the build (`npm run build`) — test files should never end up in `dist/`.

## Releasing

Published to npm as `@mikecx/thunderstorm` (the unscoped name `thunderstorm` was already taken by an unrelated package). Versioning, `CHANGELOG.md`, and publishing are handled by [Changesets](https://github.com/changesets/changesets):

1. Alongside any user-facing change, run `npx changeset` (or `npm run changeset`) and describe it — pick patch/minor/major and write the summary as it should read in the changelog. Commit the generated `.changeset/*.md` file with the change.
2. On push to `main`, [.github/workflows/release.yml](.github/workflows/release.yml) either opens/updates a "Version Packages" PR (bumping `package.json` + writing `CHANGELOG.md` from the pending changesets) or, if that PR was just merged, builds and publishes to npm via `npm run release`.
3. Nothing publishes without a changeset — a plain commit with no `.changeset/*.md` file just runs CI, no release PR is touched.

One-time setup this repo needs before the workflow can actually publish (not something an agent can do): an npm account owning the `@mikecx` scope, an npm automation token, and that token saved as the `NPM_TOKEN` secret in the GitHub repo settings.

## Migrations

`migrations/` is the schema source of truth, applied via the standard Knex CLI (`npm run migrate:latest`, etc. — see README). `src/example/demo.ts` runs the _same_ migrations directory programmatically against a fresh in-memory DB, so if you add a table for a demo/test, add a real migration for it rather than an ad-hoc `knex.schema.createTable` inline in the demo.
